# 브라우저 자동 플레이(렌더링 검증) 설계

날짜: 2026-10-20 · 상태: 승인됨 2026-10-21 (빌더 점검 반영) · 계기: "그래픽 깨지는 거 없이 처음부터 끝까지 원작과 동일하게 동작해?" — 지금까지의 끝까지 검증(캠페인 워크)은 화면을 그리지 않는 헤드리스 테스트였다 · 선행: 하위 프로젝트 1~7, 캠페인 워크(`web/test/campaignWalk.test.ts`), 원작 UI 재현

## 1. 의도

새 게임부터 엔딩까지를 **실제 브라우저가 매 프레임을 그리면서** 자동으로 플레이하고, 정해진 순간마다 화면(메뉴 바·대화상자 포함)을 저장해, 사람이 "깨진 그림"을 찾아낼 수 있는 보고서를 만든다. 기계가 먼저 거를 수 있는 결함(예외, 그림 못 읽음, 빈 화면, 창 밖으로 나간 대화상자, 멈춤)은 자동으로 표시한다. 발견한 결함은 고치고 그 구간만 다시 돌린다.

"원작과 픽셀 단위로 같은가"는 이 설계의 범위 밖이다. 원작 실행 화면 캡처가 없어 비교할 수 없다. 이 설계는 "웹판이 끝까지, 그림이 깨지지 않고 돈다"를 증명한다.

## 2. 목표 · 비목표 · 안티목표

목표
- 캠페인 워크의 플레이어 규칙(33판을 이기는 결정 논리, 재시도·되돌리기·마을 순회·상점·경험치 배분)을 **그대로** 브라우저 페이지의 게임에 연결한다. 결정 논리를 두 벌 두지 않는다.
- 매 프레임을 실제 시간과 같은 간격(1000/60 ms)으로 그리되 기다리지 않는다(가상 시계). 연출 장면·페이드·애니메이션은 건너뛰지 않고 전부 그린다.
- 정해진 순간마다 전체 게임 창을 PNG 로 저장하고, 순간마다 게임 상태(스테이지·전투 번호·턴·가상 시각·모드)를 기록한다.
- 자동 판정 결과와 섬네일을 장(章)별로 모은 보고서를 만든다. 걸린 프레임이 맨 위에 온다.
- 헤드리스 캠페인 워크 테스트는 그대로 초록이고, 그 결과(재시도 횟수·전투 33판)는 바뀌지 않는다.

비목표
- 원작 화면과의 비교. 사람의 플레이 감각(난이도) 평가. 소리 검증(가상 시계에서 소리는 끈다).
- 자동 플레이를 제품 기능으로 노출하는 것. `play.html?walk=1` 은 개발용이다.

안티목표(이러면 실패)
- 헤드리스 워크와 브라우저 워크의 결정 논리가 갈라져 한쪽만 고쳐지는 것.
- 1,000장을 사람이 다 봐야만 결함을 찾는 보고서. 자동 판정 없이 섬네일만 나열하면 실패다.
- 자동 플레이가 게임 코드에 "테스트용 분기"를 심는 것. 게임은 게임 코어의 공개 호출(`dispatch`·`townSelect`·`loadGame` — 헤드리스 워크가 쓰는 것과 같은 호출)과 플레이어의 입력 경로(대화상자 단추 클릭, 캔버스 클릭, 단축키)로만 움직인다. 허용되는 게임 코드 변경은 계측뿐이다(자산 로더의 대기 카운터, 프레임 루프의 외부 호출).

## 3. 제약

- 브라우저 드라이버는 **ego 브라우저**(`ego-browser nodejs` 스크립트: `page.goto/evaluate/waitForFunction/screenshot`)다. Playwright 를 설치하지 않는다. 한 스크립트의 실행 시간에 제한이 있을 수 있으므로 수집은 라운드로 나눌 수 있어야 한다. 페이지는 그림 요청마다 드라이버의 재개를 기다리며 멈추므로(캡처 손실 0), 라운드 사이에는 다음 그림 요청에서 멈춰 있다. 라운드가 같은 작업 공간·탭을 이어받아 수집을 계속하고, 매니페스트는 페이지가 들고 있다가 라운드마다 내려받는다.
- 탭이 뒤로 가면 브라우저가 타이머를 늦춘다. 실행 중에는 탭을 앞에 둔다. 프레임 양보는 `MessageChannel` 로 하고, 그림 요청 때만 `requestAnimationFrame` 한 번을 기다린다.
- 개발 서버는 5173 이 아닌 포트(5199)를 쓴다. 사용자가 5173 을 다른 데 쓴다.
- 저장소 파일은 건드리지 않는다(세이브는 자동 플레이 페이지 안의 메모리 백엔드). 결과물은 스크래치패드 아래 `walk-browser/<실행시각>/` 에 둔다.
- 기존 규칙: TDD(모델 테스트 RED→GREEN), `python3 -I`, `rtk proxy`, 커밋 끝 `Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>`, 문서는 ASD-STE100 한국어.

## 4. 결정된 것 (사용자와 합의)

- 드라이버: ego 브라우저. 결과물: 장별 섬네일 보고서(걸린 프레임 먼저) + 원본 PNG.
- 찍는 순간: 맵이 새로 뜰 때, 전투마다 첫 턴·마지막 일격·결과 대화상자, 마을에 들어갈 때, 연출 장면의 부(部)마다, 대화상자가 열릴 때마다, 그리고 가상 시각 10초마다.
- 자동 판정: 예외·오류 로그, 그림 못 읽음 경고, 페이드 중이 아닌데 한 색으로 가득 찬 프레임, 640×480 밖으로 나간 대화상자, 60초(가상) 동안 변화 없음.
- 발견한 결함은 바로 고치고 그 구간만 다시 돌린다(자동 플레이는 세이브에서 시작할 수 있어야 한다).

## 5. 설계

### 5.1 구성

| 파일 | 역할 |
|---|---|
| `web/src/dev/walker.ts` (새) | 캠페인 워크의 **결정 논리**를 테스트에서 떼어낸 모듈. `class Walker` 가 게임 코어를 받아 한 프레임의 결정을 내린다. 바깥세상과는 작은 인터페이스로만 만난다(아래 5.2). |
| `web/test/campaignWalk.test.ts` | 얇아진다: `MapStage` + `Walker` + 기존 단언(경고 0, 전투 33, 스테이지 0~17). 개발 손잡이(`WALK_FROM` 등)는 유지. |
| `web/src/play/walk.ts` (새) | 브라우저 자동 플레이. `play.html?walk=1[&seed=7][&from=<url>]` 에서 `main.ts` 가 동적 import 한다. 가상 시계 루프, `Walker` 와 실제 페이지(BrowserStage·Dialogs·Dialogue)의 연결, 포착 순간, 자동 판정, `window.__walk` 프로토콜. |
| `web/src/play/main.ts` | `walk` 플래그일 때 프레임 루프를 가상 시계에 넘기고(`frame(now)` 를 외부에서 부를 수 있게), 소리를 끄고, `Rng` 씨앗을 플래그에서 받는다. 그 밖의 플레이 경로는 바뀌지 않는다. |
| `tools/walk_browser.mjs` 라운드 파일 (실행 때 생성, 스크래치패드) | ego 스크립트: 페이지 열기 → `__walk.pending` 기다림 → `page.screenshot` → 재개. 콘솔 오류 수집. 라운드마다 새 파일. |
| `tools/walk_report.py` (새) | 매니페스트 + PNG → 섬네일(`sips`) + `report.html`(로컬, 원본 링크) + 아티팩트용 요약 HTML(섬네일·걸린 프레임만 포함, 16 MB 이하). 표준 라이브러리만. |

### 5.2 Walker 와 바깥세상의 경계

Walker 는 게임을 `GameCore` 로만 만지고(`dispatch`, `townSelect`, `loadGame`, `campaign`, `battle`, `mode`), 화면과는 다음 인터페이스로 만난다. 헤드리스(`MapStage`)와 브라우저(`walk.ts`)가 각각 구현한다.

```ts
interface WalkWorld {
  click(): void;                                   // WAIT_CLICK 한 번 넘기기: 헤드리스 = stage.clicks = 1, 브라우저 = dialogue.noteClick()(플레이어의 캔버스 클릭과 같은 경로)
  answer(kind: ModalKind, value: number): void;    // 모달 응답: 헤드리스 = stage.modal = value, 브라우저 = 열린 대화상자의 단추를 누른다(아래 5.3)
  presenterBusy(): boolean;                        // 전투 연출 중이면 결정을 미룬다
  autosave(slot: 30 | 31): Uint8Array | null;      // 재시도·되돌리기용 세이브 바이트(헤드리스 = stage.saves, 브라우저 = writeSave 가로채기)
  reseed(seed: number): void;                      // 재시도마다 Rng 교체(헤드리스 = res.rng, 브라우저 = main.ts 의 res)
  log(line: string): void;
}
```

Walker 가 세상에서 **듣는** 것은 세 가지뿐이다: `onModal(kind, payload)`, `onLog(kind, text)`(`save 30`·`save 31`·`TEST_IS_ACTOR`·경고), 그리고 매 프레임의 `step(now)`. 헤드리스에서 `stage.visual = null`(장면 즉시 종료)과 `stage.fading = false`(페이드 즉시 종료)는 **MapStage 쪽**의 일로 남고, 브라우저에서는 장면과 페이드가 가상 시계로 실제 길이만큼 돈다. Walker 는 `core.mode === 'script'` 인 동안 클릭만 넣는다.

### 5.3 브라우저에서 모달에 답하기

실제 대화상자가 열리므로 Walker 의 답을 단추로 바꾼다(`walk.ts`):

| 모달 | Walker 의 답 | 브라우저 동작 |
|---|---|---|
| `ask`(126 확인) | 0/1 | 아니오/예 단추 클릭 |
| `message` | 0 | 닫기 클릭 |
| `save`(143 저장 모드) | −1 | 취소 클릭 |
| `shop`(150) | `shopping()` 으로 소지품을 바꾼 뒤 1 | 돌아오기 클릭(목록은 보여 주되 사지 않는다 — 구매는 Walker 가 코어로 했다) |
| `result`(162 경험치 배분) | 한 유닛에 풀 전부 | 그 유닛 행의 막대를 풀로, 나머지 0 으로 맞춘 뒤(`input` 이벤트) 결정 클릭. 행 순서는 대화상자와 같은 규칙(`party.filter(u !== null && status !== 9)`). Walker 의 받는 이도 **같은 집합**에서 고른다(숨은 유닛 status 9 는 실제 대화상자로는 받을 수 없다) — 헤드리스의 `liveUnits` 기준에서 이 한 가지만 바뀐다 |

대화상자를 못 찾거나 단추가 없으면 `warn:walk` 로 적고 `dialogs.closeAll()` 하지 않는다(멈춤으로 드러나게 둔다).

### 5.4 가상 시계와 프레임 루프

- `walk.ts` 가 `now` 를 0 에서 1000/60 씩 올리며 `main.ts` 의 `frame(now)` 를 부른다. `requestAnimationFrame` 은 쓰지 않는다. 프레임 사이 양보는 `MessageChannel` 메시지 한 번.
- 소리: `stage.setVolumes(0, 0)` 와 오디오 잠금 해제 생략. 음악 페이드는 가상 시계로 돈다.
- 그림 요청: 순간이 되면 `__walk.pending = { id, tag, state }` 를 두고 `requestAnimationFrame` 을 한 번 기다린 뒤 루프를 멈춘다. ego 스크립트가 찍고 `__walk.resume()` 을 부르면 이어간다. 스크립트가 없으면(`&shots=0`) 멈추지 않고 넘어간다.
- 세이브: 메모리 백엔드 강제(`?walk=1` 이면 IndexedDB 를 열지 않는다). `writeSave` 를 가로채 30/31 번 바이트를 Walker 에 준다.
- 타이틀 화면은 열지 않는다: 자동 플레이는 새 게임(또는 `&from`)으로 바로 시작하고, 패배·되돌리기 뒤의 불러오기는 헤드리스와 같이 Walker 가 `core.loadGame` 으로 한다. `main.ts` 의 "`ended` → 타이틀" 전환은 walk 모드에서 건너뛴다(타이틀·143 흐름은 손으로 검증했다).
- **자산 대기**: 가상 시계는 자산 층에 미결 로드가 없을 때만 전진한다. 자산 로더(`AssetLoader`·`BitmapCache`·시트·APD·비주얼 비트맵)에 미결 카운터를 두고, `#win`·`#dialogue` 안의 `<img>` 가 `complete` 가 아니어도 미결로 센다. 미결이 있으면 가상 시각을 멈춘 채 실제 시간을 짧게 양보한다. 그래야 그림이 도착하기 전에 WAIT_CLICK 이 지나가지 않고, `blank` 가 로딩 중 검은 화면을 오탐하지 않는다. 예외: `Dialogue.showEpisode` 의 2.5초 배너는 실제 시간이라 가상 시계보다 오래 남는다 — 그대로 둔다(보고서에 더 자주 보일 뿐이다).
- 시작점: 기본은 새 게임(처음부터). `&from=<url>` 이면 그 세이브(`assets/save/zz-*.bin` 같은 개발용 파일)를 불러와 그 전투부터 시작한다(구간 재실행).

### 5.5 포착 순간과 상태 기록

| 태그 | 조건(프레임마다 관찰) |
|---|---|
| `map` | `stage.mapReady()` 가 거짓→참 |
| `battle-start` | 전투의 첫 플레이어 페이즈(`turn === 1`, `sel.mode === 'idle'`) 첫 프레임 |
| `battle-end` | `phase.kind === 'end'` 첫 프레임 |
| `town` | `showTown` 호출(가로채기) 뒤 첫 프레임 |
| `scene-N` | 비주얼 씬의 `player.part` 가 바뀐 뒤 가상 1초 |
| `dialog-<id>` | `Dialogs.opened` 뒤 첫 프레임(템플릿 번호) |
| `tick` | 가상 시각 10초마다 |
| `ui-*` | 장마다 한 번, 첫 플레이어 턴에서 플레이어가 여는 화면: F2 유니트 일람(탭 4개 → 4장), F3 전체 맵(1장), 행동할 파티원의 오른쪽 클릭 팝업(1장). 실제 입력 경로(`keydown`, `contextmenu`)로 열고 Esc 로 닫는다. 최근에 만든 창들의 그림과 `overflow` 판정이 여기서 검증된다 |
| `flag-*` | 자동 판정이 걸린 프레임(아래) |

매니페스트 항목: `{ id, tag, file, t(가상 ms), stage, battle(몇 번째), turn, mode, flags[] }`. 장(章) = 전투 번호(0 = 오프닝·첫 마을). 보고서는 장별로 묶는다.

### 5.6 자동 판정

프레임마다(그림 요청과 무관하게) 검사하고, 걸리면 그 프레임을 `flag-<종류>` 로 찍는다. 같은 종류는 장마다 최대 3장만 찍고 나머지는 세기만 한다.

| 종류 | 판정 |
|---|---|
| `error` | `window.onerror`/`unhandledrejection`/`console.error` — 한 건이라도 있으면 실행 실패 |
| `warn` | 게임의 `log('warn', …)`(그림 못 읽음, 자산 경고) |
| `blank` | 캔버스를 32×24 격자로 표본해 99 % 이상이 한 색이고, 그 순간 페이드 알파 < 1 이며 비주얼 씬 재생 중이 아닐 때 |
| `overflow` | 열린 `.w95-dialog`·`.w95-popup`·`.w95-window` 의 사각형이 `#screen` 밖으로 나갔을 때 |
| `stuck` | 비주얼 씬이 아닐 때: 가상 60초 동안 `core.mode`·VM pc·전투 턴·대화상자 수·페이드 알파가 모두 그대로. 비주얼 씬 재생 중: `player.part` 가 가상 220초(가장 긴 부 200초 + 여유) 동안 그대로. 걸리면 실행을 멈추고 실패로 기록 |

Walker 자체의 `warn:walk` 줄(거부된 명령 등)도 `warn` 으로 센다. 헤드리스 워크의 기준(경고 0)과 같다.

### 5.7 결과물

- `walk-browser/<YYYYMMDD-HHMM>/shots/0001-map.png …`, `manifest.json`, `console.log`(페이지 콘솔), `walk.log`(Walker 로그).
- `report.html`(로컬): 맨 위에 요약(전투 수, 장면 수, 걸린 프레임 수, 실행 시간), 그 아래 걸린 프레임, 그 아래 장별 섬네일 격자(섬네일 클릭 → 원본 PNG).
- 아티팩트: 같은 구성이지만 섬네일(160×120 JPEG)과 걸린 프레임만 포함, 16 MB 이하. 기존 완성 보고 아티팩트에 §13 으로 연결한다.
- 성공 기준: `error`·`stuck` 0, `warn` 0, 전투 33, `game complete`. `blank`·`overflow` 는 사람이 보고 결정한다.

## 6. 빌더에게 맡기는 것

- Walker 추출의 세부: 테스트 안의 지역 상태(hold·focus·tank·needed 등 수십 개)를 클래스 필드로 옮기는 방법. 기준은 하나다 — **추출 단계** 뒤 헤드리스 워크의 콘솔 요약(재시도·strikes·stages)이 글자 하나 다르지 않을 것. 그 다음 단계(경험치 받는 이를 대화상자 행 집합에 맞춤)는 요약이 바뀔 수 있고, 기준은 워크가 여전히 초록(경고 0, 전투 33)인 것이다.
- `main.ts` 에서 프레임 루프를 밖에 내어 주는 방법(함수 export 또는 `__ft2()` 확장). 플레이 경로의 동작은 바뀌지 않는다.
- ego 라운드 스크립트의 길이(한 라운드에 몇 장) — 실행 시간 제한을 만나면 줄인다.
- 섬네일 생성 도구: macOS `sips` 를 쓴다. 없으면 보고서는 원본을 축소 표시한다.

## 7. 내 선택(사용자가 정하지 않은 것)

- 가상 시계 간격 1000/60 ms. 헤드리스는 50 ms 로 돈다. 결정 논리는 간격에 의존하지 않으므로 결과는 같아야 한다. 다르면 재시도 규칙이 흡수한다.
- 브라우저 워크의 `Rng` 씨앗 7(헤드리스와 같음). 되돌리기·재시도 때의 재씨앗 규칙도 같다.
- 상점 대화상자에서 실제로 사지 않고 Walker 가 코어로 산다. 대화상자의 **그림**이 검증 대상이고 구매 논리는 헤드리스가 이미 검증했다.
- 걸린 프레임은 종류마다 장당 3장까지만 찍는다.
- 전체 실행은 한 번에 20~40분을 예상한다. 라운드로 나누어도 결과는 한 매니페스트에 모인다.
- 검토자(빌더 점검)의 질문에 대한 내 결정: ① 패배·되돌리기의 불러오기는 `core.loadGame`(헤드리스와 같은 경로), 타이틀은 walk 모드에서 열지 않음. ② 자산 로딩 중에는 가상 시계를 멈춤(로더 계측). ③ 라운드 사이 페이지는 다음 그림 요청에서 멈춰 기다림(캡처 손실 0). ④ 경험치 받는 이는 대화상자 행 집합에서 고름. ⑤ `stuck` 은 비주얼 씬을 따로 봄. ⑥ 플레이어가 여는 UI(F2·F3·팝업)를 장마다 한 번 찍는 것을 범위에 넣음.
