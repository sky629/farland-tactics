# 하위 프로젝트 7 — 원작 UI 재현 설계 (화면 안의 인터페이스)

날짜: 2026-10-19 · 상태: 구현 완료(태스크 1~8; 전체 맵 F3 은 비활성, 유니트 일람의 '이동' 버튼은 비활성, 소유자 그리기 그림은 비워 둠 — §9) · 계기: 사용자 지적 "ui 자체도 실제 게임이랑 너무 다르잖아. 게임화면 밖에 왜 인터페이스가 있는거야?" · 선행: 하위 프로젝트 1~6, 캠페인 워크(실제 플레이)

## 1. 목표와 완료 기준

플레이 페이지(`web/play.html`)에서 **게임 창 밖의 인터페이스를 없앤다.** 원작의 인터페이스는 두 층이다.

1. 화면 안에 그리는 것: 커서, 이동·공격 범위 타일, 방향 화살표, 상태 아이콘(`system.apd`), 대사창·메시지창(`window1.apd`, `window2.apd`). 웹판은 이미 캔버스에 그린다.
2. Win32 창 크롬: 메뉴 바(RT_MENU 103), 코드가 만드는 팝업 메뉴(유닛 명령), 대화상자 21개(RT_DIALOG). 웹판(하위 프로젝트 4)은 이것을 HTML 옆 패널과 오버레이로 바꿨다. 사용자가 본 "게임 화면 밖의 인터페이스"가 이것이다.

이 하위 프로젝트는 2층을 원작 모양(Windows 95 룩: 회색 3D 베벨, 굴림 9~12 pt, 파란 선택 막대)으로 **게임 창 안에** 다시 만든다. 게임 창 = 메뉴 바 + 640×480 서피스. HTML 옆 패널은 개발 도구로만 남긴다(`play.html?dev=1`).

완료 기준:

1. 기본 플레이 화면은 메뉴 바와 640×480 서피스뿐이다. 정수 배율은 메뉴 바와 대화상자에도 같이 적용된다.
2. 메뉴 103의 항목이 모두 있고 동작한다. 맵 → 표시(유니트 일람 F2, 전체 맵 F3, 전체 화면 ON/OFF F4, 클리어 조건) · 턴 종료 F10 · 시스템(불러오기 F1, 저장하기 F5, 환경설정 F11, 게임종료). 디버그 메뉴는 `?dev=1`에서만 보인다.
3. 유닛 명령은 원작의 클릭 문법과 오른쪽 클릭 팝업이다(디컴파일 `FUN_00430c80`, story_flow.md §7a). 왼쪽 클릭: 파티원을 고르면 이동 범위가 곧 보이고, 적을 클릭하면 공격, 칸을 클릭하면 이동, 제자리를 클릭하면 대기(방향 지정). 오른쪽 클릭(범위 선택 중이 아닐 때): `맵` 메뉴의 항목 위에 커서 아래 파티원의 `〈이름〉의 행동 (HP:x/y)`, `〈이름〉의 마법/특기 (MP:x/y)` ▸ 주문 `이름(약칭) MP:n`, `도구를 사용하다(U)` ▸ 소모품 `이름 n개`, 구분선이 끼워진다. 회색 조건도 원작대로(이동 완료, 행동 완료, 침묵, 상태 1/3/4/5/8/9, MP 부족). 공격은 메뉴 항목이 아니다.
4. 플레이에 쓰이는 대화상자를 RT_DIALOG 템플릿 **데이터**로 그린다: 107 유니트 일람(탭 117 상태 · 119 장비 · 118 매각), 124 스테이지 선택(타이틀: 게임 개시/불러오기), 126·163 확인(예/아니오), 143 데이터 선택(불러오기·저장: 결정/취소/처음부터), 150 물품목록 · 151 몇개 삽니까? · 152 누가 사나? · 153 몇개 팔았습니까?, 156 환경설정(웹: 음악·효과음 볼륨, 음소거, 전체 화면), 160 BGM 선택, 162 경험치 배분(막대 7개, 밸런스 배분/균등배분/결정). 154 디버그 정보는 `?dev=1`.
5. 지금 패널이 보여 주던 정보는 원작의 자리로 간다: 유닛 능력치·장비·소지품 → 유니트 일람, 클리어 조건 → 메뉴 "클리어 조건"(메시지창), 턴 수 → 턴 시작 메시지(이미 있음), 음량 → 환경설정, 로그·오류 → 개발 패널.
6. 테스트: 템플릿 파싱(Python, 21개 전부), 레이아웃 변환(dialog unit → px)과 컨트롤 트리, 메뉴·팝업의 활성 상태가 `menuEnabled()`와 같음, 단축키, 대화상자 결과(Promise)의 흐름(취소·Esc 포함), 캠페인 워크가 그대로 통과(UI는 코어와 분리되어 있다).
7. 브라우저 확인(내 탭): 새 게임 → 타이틀 대화상자 124 → 첫 전투에서 유닛 팝업 → 유니트 일람 탭 셋 → F10 턴 종료 → F5 저장(143) → F11 환경설정.

## 3. 접근 방식

| 안 | 내용 | 평가 |
|---|---|---|
| **A. 게임 프레임 안에 겹치는 DOM 위젯(Win95 룩 CSS)** (채택) | 메뉴 바·팝업·대화상자를 HTML 요소로 만들고, 프레임의 정수 배율 s에 맞춰 `transform: scale(s)`로 함께 키운다. 레이아웃은 템플릿 JSON에서 만든다. 리스트·탭·입력·스크롤은 브라우저가 한다. | 글꼴 대체(굴림 → Gulim/Apple SD Gothic Neo)로 픽셀은 근사, 구조·좌표·문자열은 원작 그대로. IME·접근성·클립보드가 공짜. 테스트는 jsdom 없이 순수 레이아웃 함수로. |
| B. 캔버스에 전부 그린다 | 위젯 툴킷을 직접 구현 | 리스트·스크롤·입력을 다시 발명한다. 비용이 크고 이점은 픽셀 몇 개. |
| C. 지금의 옆 패널 유지 | — | 사용자 지적이 그대로 남는다. |

## 4. 데이터

- 새 도구 `tools/ft2_dialogs.py`(표준 라이브러리): PE 리소스 디렉터리 → RT_DIALOG(5) 21개 → `data/dialogs.json` `{ "107": { ex, style, title, font: [pt, name], cx, cy, items: [{ id, cls, text, x, y, cx, cy, style }] } }`; RT_MENU(4) 103 → `data/menu.json` `{ items: [{ text, id?, flags, items? }] }`. `tools/ft2_export.py`가 호출한다. 테스트(`tools/test_ft2_dialogs.py`): 21개가 읽히고, 107의 컨트롤 4개와 162의 막대 7개가 있고, 메뉴 103에 "턴 종료"가 있다.
- dialog unit → px: 가로 1 du = 글꼴 평균 문자폭/4, 세로 1 du = 글꼴 높이/8. 웹에서는 대체 글꼴을 `measureText`로 재어 같은 비율로 맞춘다. 템플릿마다 글꼴이 다르므로(9~12 pt) 대화상자마다 잰다.
- 문자열의 `&`는 니모닉이다(Alt+글자). 표시에서는 밑줄, 입력에서는 단축키.

## 6. 배율과 좌표

- 프레임 = 메뉴 바(Win95 메뉴 바 높이 19 px) + 640×480. `#screen`의 정수 배율 s를 프레임 전체에 건다. 대화상자는 원작처럼 창 중앙에, 팝업은 클릭 지점에 띄운다(프레임 밖으로 나가면 안쪽으로 민다).
- 전체 화면(F4)은 `requestFullscreen` + 가장 큰 정수 배율.

## 8. 테스트와 확인

- Python: 템플릿 파서 테스트.
- Vitest: `layout.ts`(du→px, 107·162의 컨트롤 좌표), 메뉴 모델(활성 상태, 단축키 → 명령), 팝업 모델(항목 → 명령), 대화상자 바인딩의 결과 흐름(가짜 DOM 없이 모델 수준), `expShare` 162 바인딩(막대 값 ↔ 배분).
- 캠페인 워크는 코어만 쓰므로 영향이 없어야 한다(통과 확인).
- 브라우저(Playwright/Chrome, 내 탭): §1-7의 순서대로 화면을 찍어 보고에 넣는다.

## 9. 범위 밖과 추정

- 전체 맵(F3)의 원작 화면은 미확인이다. 축소 맵 캔버스로 근사한다 [추정].
- 디버그 메뉴는 `?dev=1`에서 무적·부자·강제 클리어·턴 회복만 넣는다.
- 소유자 그리기 그림(경험치 막대·초상·속성 아이콘)의 출처를 찾지 못하면 단색·글자로 대체하고 [추정]으로 적는다.
- 굴림 비트맵 글꼴의 픽셀 재현은 하지 않는다(글꼴 대체).
